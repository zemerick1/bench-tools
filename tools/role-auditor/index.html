Role & Policy Auditor

Which roles can reach anywhere, and how many clients are sitting on that decision. Open a row for the policy, the service, and the rest of the ACL. ANY is the easy catch. The interesting stuff is whatever you tag yourself.

What this is: a read-only look at the shared library (view-type=LIBRARY) and a headcount of connected clients. The built-in checks notice ANY. Extra rules are for the subnet, host, or role you already side-eye. A canned allow-any that only names a service stays inside the role, protocol and ports included, so “DNS to anywhere” does not get to cosplay as “the network is open.”

What this is not: hit counts, the config a site actually runs, or a change tool. A quiet report is not a sign-off. This tab has not walked your network. A deny to ANY still shows up, because the address is ANY — read the action before you page someone.
The secret stays in this browser. No account, no database, no Bench Tools vault with your name on it. Client ID and secret land in localStorage on this device, as plain text, because a browser is not a safe. The access token is held in memory for the check and is not written down. A live check posts those credentials to /proxy on the host that served this page. The proxy hands them to HPE and does not keep a copy. Anyone who can use this browser profile can read the secret. Forget it when you are done on a shared machine.

ANY is the free square. One check flags a source or destination of ANY. The other wants destination ANY and any service, and tags that row Any service. Turn either off when it gets noisy.     FAQ

    Where do the credentials go?

    Into localStorage on this origin. A live check posts them to /proxy on the same host. That proxy forwards the call to HPE and does not keep a copy. There is no database. Forget them on a shared machine. The access token is not stored.

    What does ANY mean here?

    A policy endpoint whose type is ADDRESS_ANY, or a role whose name is any. A protocol of ANY is any IP protocol. The address check does not use it. Source or destination is enough to flag that rule. Both sides is called out as any-to-any in the row. The other built-in check wants destination ANY and any service: no named net-service, application, or app category, and the protocol is ANY or left unset. TCP, or a named service such as DNS, does not match. A role ACL with no protocol counts as any service. A protocol and port are the service. UDP port 67 shows as UDP 67. A row is red only when an enabled rule matches that line. Built-in checks and extra rules work the same way. Turning a check off clears the red on lines that only that check matched.

    How are permissions tied to a role?

    A rule counts as that role’s permissions when the source is that role, or when the policy or role ACL has the same name as the role. Client counts come from connected clients (/network-monitoring/v1/clients) and only match when the role string is the same.

    Why might the live check fail in the browser?

    The cluster API does not send CORS headers, so the browser is not invited. This page posts to /proxy on this same address. python3 -m http.server refuses that POST. python3 server.py on the same port serves the files and forwards the check. The proxy does not store the secret.

    Hit counts?

    Not yet, and it will not invent them to look useful. A role ACL can carry count: true, which means the switch was asked to count. That is not a number. A match key this engine does not know is skipped and named.
