Show-Tech Sticky Note

show tech-support is a novel written by a machine that hates you. You want the sticky note: what is this box, what code is it on, how long has it been up, and which lines already used words like CRITICAL and core dump.

What this is not: a root-cause engine, a health score, or a thousand if statements cosplaying as TAC. We pull clear facts and highlight lines that already look wrong. Quiet dumps can still be on fire. Loud dumps can be noisy theater. You’re the adult in the room.
Stays in this tab. Paste or drop a text dump. No upload server, no “AI in the cloud,” no surprise zip interpreter (unzip yourself; we’re not your intern). Refresh the page and the evidence leaves with your dignity.

How to collect logs

How to collect a log with PuTTY (logging setup)

This tool wants a plain-text session log, not a screenshot of suffering. PuTTY is the usual accomplice.

  1. Open PuTTY → left tree Session → Logging.
  2. Session logging: choose All session output (or “Printable output” if you enjoy missing the fun ANSI crumbs — either works).
  3. Log file name: pick something memorable, e.g. C:\logs\show-tech-rack6300.txt. Check Append if you reconnect a lot.
  4. Optional but nice: under Session → Logging, enable Flush log file frequently so a crash doesn’t eat the last page of evidence.
  5. Save the PuTTY session if you like, then open the SSH/serial connection. Logging starts when the session starts.
  6. On the device, disable paging if you can, then run tech-support (names vary by persona):
    • AOS-CX switch: no page then show tech / show tech-support
    • AOS-10 AP / Instant / Microbranch: show tech-support
    • AOS-10 gateway / VPNC (and AOS-8 controllers): show tech-support (plain show tech may whine — that’s normal)
  7. Wait until it finishes. Close the session. Drop the .txt / .log file onto this page (or paste).

We don’t auto-drive PuTTY or unpack vendor support .tar.gz bundles. You capture text; we make the sticky note.

FAQ

Is this official HPE support?

No. It’s a browser sticky note with a sense of humor and a keyword list. Always confirm on real dumps, real docs, and real humans before you reboot production “just to see.”

What do you flag as “looks wrong”?

Grouped findings from lines that already contain trouble words — non-zero core dump counts, CRITICAL severity, fan/PSU faults, real temperature alarms, IKE FAILED, err-disabled, and a capped sample of ERROR/FAIL. Table headers (REQ-FAIL), alarm: false, bare /fs/coredump: paths, and command titles alone are filtered out. Each group expands to show the hit plus neighboring lines. We still do not invent root cause.

Personas we try to sniff

AOS-CX switches (FL.10.x); AOS-10 campus AP (may bridge locally or tunnel user traffic with GRE/IPSec to a gateway); Instant / AOS-8 IAP (bridges by default; IAP-VPN if configured); AOS-10 Microbranch AP + VPNC (SD-Branch overlay — IPSec health matters); AOS-10 gateway/MD (campus gateway / mobility role on AOS-10).

Where do the docs fit in?

Under tools/show-tech/docs/: AOS-CX / AOS-S event log references help decode switch Event|#### lines (switching only). The SD-Branch VSG PDF is the mental model for Microbranch + VPNC overlay, IPSec, and branch-to-VPNC connectivity.

Will you miss problems?

Yes. Constantly. Absence of flags is not a clean bill of health. It’s “our little regexes didn’t yell.” Use your eyes. Use TAC. Use the SE you wish you had.
